# 各游戏进入/日常/月度流程与踩坑

> 由 AGENTS.md 拆分；改动相关代码前先读本篇。

## 统一入口：所有流程必须从主世界/主界面开始（2026-11-04 用户定规）

用户原话：「所有流程必须在主世界开始，这样才会统一。哪有在其他页面开始的？」

参照白荆的实现（`baijing_flow.run_baijing_ingame_flow`）：**目标态优先**——
主界面模板连续命中才算进入成功；弹窗点「点击屏幕继续/关闭异常」；未知态
连续 ESC（最多 10 次）；确认到主界面后才开始日常/月度。任何流程都不能假设
自己从启动器、登录页或某个子页面开始。

各游戏现状：
- 白荆：任意态 ESC 恢复到主界面（模板连续 5 帧）后才继续。
- 原神 / 崩铁：`enter_main_interface` 第一步先查主界面模板（派蒙 / 主界面图标），
  已在主界面连续 2 帧命中即快速通过，否则才点登录页。
- 暖暖：`nikki_calendar._run_flow_inner` 先 `_has_main`，确认不了就关游戏交给 whimbox。
- 绝区零：ZZZ_MONTHLY 原来直接从「点击进入游戏」开始 → 已在主世界会空点失败。
  现在流程配置 `start_from_main`（`绝区零-主界面-电台.png`）命中直接跳到第 3 步兑换。
- 异环：NTE_MONTHLY 原来固定走启动器 1-6 步 → 游戏已在运行会死等「开始游戏」。
  现在配置 `skip_steps_if_process`（`HTGame.exe` 在跑就跳过 1-4 步），
  「进入游戏」步骤改 `optional_if_missing`（已在游戏里没有该按钮就跳过）。

通用机制在 `foreground_flow_runner._resolve_start_guard`：
- 流程级 `start_from_main: {template, skip_to_step}`：主界面模板命中 → 从第 N 步开始。
- 流程级 `skip_steps_if_process: {process_name, steps}`：进程已在运行 → 跳过指定步骤。
新增游戏/流程时优先用这两个守卫，不要再写「假设从启动器开始」的步骤序列。

## 页面判定铁律（2026-11-04 用户定规，强制）

用户原话：「有奇想日历就在奇想日历界面？考虑问题这么不周全？你不会用判定法测一下
其他页面，有相同文本不就误判了吗？」

1. **禁止「页面上出现某个词就判成该页」**。同名词（晶石兑换 / 本月限购 / 背包 /
   商城 / 奇想日历）会在多个页面出现，必须至少满足一条：
   - 专属特征 + 最少证据数（≥2 个专属标记）；
   - 标题 + 内容双证据（如「晶石兑换」AND「本月限购」）；
   - 标题 + 区域限定（如背包只认左上角标题区，避开 ESC 菜单里的「背包」按钮）；
   - 模板匹配优先（连续帧），OCR 只作兜底。
2. **每个判定函数必须在 `tests/suite_page_judgement_policy.py` 登记表写明证据**。
   新增 `_is_*page` / `*_visible` 函数不登记 → 该测试直接失败；裸单关键词判定
   会被 AST 扫描拦下（登记过的专属词例外）。
3. **每个游戏的实际截图必须进页面判定矩阵**（`tests/suite_<game>_page_matrix_*.py`），
   正/负样本逐张断言互斥。模板见 `tests/suite_nikki_page_matrix_20261104.py`
   （17 张图 × 10 个判定，含 flow_failures 的真实失败现场）。
4. **新增截图必须存档**到 `data/artifacts/ref_<game>_<page>_<YYYYMMDD>.png`
   （运行失败现场在 `data/artifacts/flow_failures/`），并加入矩阵。
5. 已抓到的真实误判案例（别再犯）：
   - 「晶石兑换」→ 兑换页/弹窗被误判成搭配赛页；
   - 「本月限购」→ 共鸣商店被误判成晶石兑换页；
   - 「奇想日历」→ 主世界顶部图标栏被误判成日历页；
   - 「背包」→ 崩铁 ESC 菜单被误判成背包已打开（已加左上角区域限定）。

- **彩色模板匹配 `color_match`（2026-11-01 新增，默认关闭）**：`_match_template_cv2_once(..., use_color=True)`
  → `_locate_template_in_window` / `_locate_template_on_screen` / `zzz_monthly_shop._locate` 全链透传；
  step/item 配 `color_match: true` 才开。意义不是"灰度认不出目标"，而是**目标消失后会误认隔壁同类图标**：
  异环质感骰子（红）与捏造骰子（蓝）灰度互匹配 **0.976**，红骰子撤架后灰度仍指向蓝骰子那块
  （继续点 → 点错商品），彩色只有 **0.689**，直接判定"已消失"。实测颜色：红 B67/G73/R153、蓝 B108/G96/R104，
  灰度均值 95.9 vs 99.5 —— 灰度公式对红蓝权重太低，这是根因。
  代价：单次匹配慢 2~3 倍（模板小，无感）；彩色模式下**跳过 pyautogui.locate 兜底**（它只认灰度）。
  换机器有渲染色差时下调阈值即可，互匹配 0.689 给了 0.16+ 余量，别把阈值压到 0.85 以下。

  必须重新量**（对截图跑 OCR 拿文字框、再用 `cv2.matchTemplate` 自匹配 1.0 校验）。

#### whimbox「奇迹之冠巅峰赛」12/24 也被跳过（2026-11-02）

- **现象**：用户勾选了「完成奇迹之冠」（`config.json → OneDragonDefaultSteps.step_mira_crown

  24/24，11-01/02 是 12/24），不是「今天已做过」，所以本周只要打过一次就整周跳过。

  **whimbox 更新会覆盖**，原文件已备份 `data/artifacts/whimbox_mira_crown_task_20261102.py.bak`）：
  `finished_count >= total_count` 才算打满跳过，没满继续做剩余场次；

**事故**：2026-11-02 17:53 / 18:01 两次白荆一条龙失败（flow_failures #145/#146），

**根因链（自己干扰自己）**：

1. 跑日志的 cmd 控制台把白荆启动器整个盖住（失败截图

2. `runtime/baijing_flow.py::_find_and_click` 调的是
   `ocr_and_template_match(target_text, tpl, logger, hwnd=None)`——**既没 hwnd 也没 region**，

3. 模板找不到 → 兜底的全屏 OCR 读到**控制台里自己的日志行**

   RapidOCR 把「开始游戏」读成独立文本框（conf 0.80），落点 (918, 976) / (827, 976)
   **都在控制台区域内** → 点击打在日志上 → 启动器没被点到 → 300s 超时。
4. 防护网漏了：`[OCR防护] 🚫 硬拦截日志污染文本 0 条（保留 130 条）`——硬拦截只剔
   「带日志特征串」（`GameAutomation:xxx` / `Traceback`）的条目，那行「开始游戏」不含
   特征串反而被保留；`⚠️ 识别区域疑似包含日志/控制台窗口（命中 7 条特征文本）」只告警不拦截。

**修法**（`runtime/baijing_flow.py`）：

- 新增 `_resolve_launcher_window()`：按进程 `Seed_OB_Prod.exe` 找启动器窗口，回退标题含
  「白荆回廊」（要排除游戏本体窗口，标题同款）。`_wait_launcher_window(timeout=30)` 等它出现。
- 点「开始游戏」前 `_focus_game_window()` 置顶；之后模板匹配与 OCR **都传
  `hwnd=启动器窗口` + `region=窗口矩形`**，物理上不可能再命中控制台。
- 命中点二次校验 `_point_in_window()`，窗外命中（控制台里的同名文字）一律丢弃。
- 再加一道精确防线 `_point_covered_by_other_window()`：用 `win32gui.WindowFromPoint`
  看命中点那一像素的顶层窗口是不是目标窗口——矩形命中还不够，控制台只压住启动器
  一角时坐标仍在矩形内，但合成点击会落在控制台上；压住就先抬高自己再确认一次。
- 窗口被遮挡 ≥30% → 先置顶再识别；置顶后仍 ≥90% 被挡 → 本轮**不识别**。
- **拿不到目标窗口就拒绝全屏识别**直接失败（`_find_and_click` hwnd=None 直接 return False）。
  这条是本条事故的核心教训，别再加回去。

**通用教训**：日志里出现的文字（按钮名、页签名）就是 OCR 的高危诱饵。

### 统一坐标口径（换分辨率 / 开 DSR 必读）

用户机器是 **1080p 桌面 + NVIDIA DSR / 游戏内 2160p 渲染**。桌面合成后的
**窗口 rect 仍是 1920x1080**，所以 UI 点击坐标按窗口走；内部渲染倍率不改变
窗口坐标系，无需为 DSR 单独适配。但窗口真的变成 4K（换显示器/改桌面分辨率）
时，任何 1080p 绝对像素都会点空。口径如下：

1. **正式代码/配置只写窗口比例**：`*_point_frac` / `*_region_frac` 经
   `zzz_monthly_shop._frac_point`（`_window_rect(hwnd)` 换算）、
   `monthly_exchange._region_frac`、`nikki_calendar._click_ratio` 落地；
   模板匹配走多尺度 `scales`，天然跟分辨率走。16:9 之外的比例按宽高独立缩放。
2. **OCR 返回的 `center` 已经是屏幕绝对坐标**（`_ocr_scan` docstring：box 是
   截图局部坐标，center 已换算成屏幕绝对坐标），**禁止再按窗口缩放**，否则二次
   换算点飞；`box` 的宽高可作相对偏移单位（随分辨率自适应）。
3. **相对偏移按文字框高/宽算，不写死像素**：`_pair_click_point` 的
   `-2.2 * box_h`、`_exchange_entry_point` 的 `-1.1 * box_h` 都是这个口径，
   box 取不到才退窗高比例（`PAIR_FALLBACK_POINT` / `EXCHANGE_ICON_DY_WINDOW_RATIO`）。
4. **一次性提权探针**（`data/artifacts/*_stage*.py）里的 1080p 基准数字统一走
   `game_auto.runtime.ui_coords.screen(win, x, y)` / `offset` / `min_confirm_y` 换算；
   `click()` / `click_at()` 吃屏幕坐标，`click_ref()` 吃 1080p 基准坐标，
   两者别混。底部确认按钮阈值 `y>700` 也改成 `min_confirm_y(win)`（700/1080）。
5. 回归：`tests/suite_ui_coords_scaling_20261106.py` 锁 1080p/720p/1440p/2160p、
   副屏偏移、非 16:9、配置换算与暖暖图标偏移。
