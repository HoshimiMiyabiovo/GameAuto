# AI 对话史 RAG：混合检索 + 重排 召回率对比实验报告

> 2026-11-10/11 实验，工具 `tools/ai_history_rag_eval.py`，产出明细
> `data/ai_history/eval/run_details.jsonl`（每查询×模式一行，可复算本报告所有数字）。
> 主工具 `tools/ai_history_rag.py` 未改动，BM25 基线保持干净。

## TL;DR

**混合检索 + 重排（模式 D）在本库全口径第一**：会话级 Recall@5 从基线 58.2% → **79.1%**
（+20.9pp），MRR 0.460 → **0.644**；关键词型查询 67.3% → **85.5%**，语义改述型 49.1% → **72.7%**。
代价是每查询多 ~350ms 重排（GPU）。**纯向量单干反而不如 BM25**（19.1% vs 29.1% chunk R@5）——
本库代码/日志/对话混合、块短、词面信号强，小嵌入模型单路撑不起来；**决定性的一步是重排**
（混合 RRF → 加重排：会话 R@5 再 +17.3pp）。与外部宣称的"62%→86-89%"同构：本库口径
BM25 sR@5 58.2% → D 79.1%，kw 侧 67.3% → 85.5% 接近宣称量级。

## 实验设置

- 语料：`data/ai_history/chunks.jsonl`，64,030 块 / 91 会话 / 约 6798 万字（11-10 build 口径不变）。
- 评估集：55 个内容块（分层抽样，滤 base64 垃圾块与 <400 字短块，30 会话 × 12 来源）×
  每块**配对两条查询** = 110 条：
  - **kw 关键词型**（含精确符号/文件名/配置键，BM25 主场）；
  - **sem 语义改述型**（刻意避开原文措辞的意译，向量主场）。
  撰写后由 `check-queries` 校验泄漏：sem 查询与真值块 bigram Dice 中位 0.026 / 最大 0.105，
  全部低于 0.12 阈值——语义型查询没有抄原文，对比诚实。
- 真值口径：源块 docid（chunk R@K，严格）+ 源会话 id（session R@K，实用——工具以整会话导出为单位）。
- 四种模式（同一语料、同一评估集）：
  | 模式 | 说明 |
  |---|---|
  | A BM25基线 | 主工具 query 同路径：倒排候选 3000 → 精确复评（复用 `_bm25_scores` 等，同口径） |
  | B 纯向量 | bge-small-zh-v1.5（ONNX，CUDA EP），全库 L2 归一点积 top-100 |
  | C 混合RRF | A/B 各 top-100，score=Σ 1/(60+rank) |
  | D 混合+重排 | C 的 top-50 过 bge-reranker-base（XLM-R 交叉编码器，ONNX，CUDA EP） |
- 参数：MAX_SEQ=512；查询端带 bge 官方指令前缀；RRF_K=60；RERANK_TOP=50。
- 环境：RTX 5070，onnxruntime_gpu 1.26，零 torch；嵌入 fp16 存储 62MB（embeddings.npy）。

## 分析

1. **重排是主力，融合只是候选集**。C 相对 A 的增益温和（cR@20 +6.4pp），且 kw 侧
   session R@5 反而 67.3%→63.6% 倒退——RRF 平权地把"向量 rank1 但 BM25 无支持"的噪声
   排到了 BM25 真命中前面。交叉编码器重排（C→D：sR@5 +17.3pp）成对细看 query-chunk，
   把两路噪声一起压下去。结论：**只做混合不做重排，不划算；要做就做全套**。
2. **纯向量单干不行**。B 在两种查询型上都输给 BM25（kw 尤甚：20.0% vs 38.2%）。本库
   块 ≤1350 字、大量代码/日志/配置键，词面信号强而块级语义模糊；bge-small-zh 又是
   24M 的小模型。"一个向量库打天下"在本库被证伪，但向量路的价值在"补 BM25 的漏"：
   混合后 D 的增益大部分来自 BM25 漏掉的会话被向量/重排救回。
3. **救回/倒退比 26:3**。A 在 @5 外或漏 → D 进 @5：26 条；A 在 @5 内 → D 掉出：3 条
   （两条小位次滑动 3→4 / 1→3，一条是 c944-kw：A 命中在 40 位，融合截断 top-50 时被挤掉，
   重排根本没见到——RERANK_TOP 是已知的截断损失源，调 50→80 可缓解，重排耗时线性微涨）。
4. **延迟可接受**。D 总耗时 ≈ A(885ms) + B(5ms) + D(351ms) ≈ 1.24s/查询（GPU 重排）；
   BM25 倒排候选路径本身 885ms 仍是瓶颈。查询端嵌入/融合几乎免费。
5. **kw/sem 分差印证架构判断**：BM25 词面敏感（kw 38.2% / sem 20.0%），小向量模型两路
   都弱，重排两路都补（kw 60.0% / sem 32.7% chunk R@5）。"代码检索靠符号、对话检索靠
   语义、最终靠 reranker 仲裁"在本库得到直接验证。

## 局限

- 评估集为 LLM（本工具作者）撰写的合成查询，非真实使用日志；110 条 / 55 块 / 30 会话规模
  有限，±1 条 ≈ ±0.9pp。
- 3 组"回声块"真值（AGENTS.md/README 目录树在多个审计子会话里重复出现，如 c60102-kw），
  跨会话近重复天然难判别，四模式同失——对**相对**比较无偏，但绝对值略被压低。
- 只测了 bge-small-zh 一个嵌入模型；更大模型（bge-base/large-zh）或可抬 B 与 C 的上限，
  但 D 架构下嵌入质量的影响被重排兜住，边际收益预计有限。
- RERANK_TOP=50 截断与 RRF_K=60 均为默认值，未调参（评估集规模不足以支撑细调）。

## 是否合入主工具（建议，待拍板）

**值得合入的是 D（混合+重排），不是纯向量。** 形态建议：

- `build` 顺带生成 `embeddings.npy`（fp16 62MB，GPU 3 分钟 / CPU 约 90 分钟，一次性）；
- `query` 加 `--hybrid` 可选开关：查询端 CPU 嵌入（单条 ~10-30ms）+ 现有 BM25 + RRF +
  重排；不开关则行为与现状逐字节一致（零回归风险）；
- 重排放 CPU 估 2-5s/查询（50 对 × 512tok），要么 RERANK_TOP 缩到 20，要么按需借用
  GPU（bge-small 仅 ~200MB 显存，与 OCR 引擎共存无压力，但违背"显存留给 OCR"原则）——
  需要用户拍板；
- `tokenizers` 进 dev 依赖已落 requirements-dev.txt；若主工具要合入，需评估是否升运行时依赖。

## 复现

```bash
.venv/Scripts/python.exe -I tools/ai_history_rag_eval.py fetch-models   # hf-mirror 下载 ONNX
.venv/Scripts/python.exe -I tools/ai_history_rag_eval.py gen-sample     # 抽样（seed=20261110）
# 人工撰写 queries.jsonl（55 块 × kw/sem 配对）
.venv/Scripts/python.exe -I tools/ai_history_rag_eval.py check-queries  # 泄漏校验
.venv/Scripts/python.exe -I tools/ai_history_rag_eval.py embed --batch 128  # 全量嵌入（断点续跑）
.venv/Scripts/python.exe -I tools/ai_history_rag_eval.py run            # 四模式对比
```

回归：`tests/suite_ai_history_rag_hybrid_20261110.py`（RRF 公式/命中位次/指标聚合/Dice
泄漏闸/小语料端到端"单路输时混合保住赢家"，纯逻辑无模型依赖）；BM25 基线与主工具
`query` 命令同查询 top-5 逐位一致（c3680-kw 实证 [3680,15552,20690,15640,20688]）。

## 踩坑记录

- **CUDA EP 创建失败回落 CPU**（64k 块 576 → 13 块/s）：pip 装的 CUDA 12.9 库在
  `site-packages/nvidia/*/bin/`，ORT 用 `LOAD_WITH_ALTERED_SEARCH_PATH` 载 provider
  DLL，该搜索序**不走** `os.add_dll_directory` 注册的目录——必须把 nvidia bin 目录
  **前置进 PATH** 才生效（两者都做最稳）。见 `_add_nvidia_dll_dirs`。
- hf-mirror 的 resolve 走 307 → huggingface.co 缓存节点重定向，本机代理只配在注册表
  （127.0.0.1:7897），urllib 60s 读超时复现；换 curl 子进程（-L --retry -C -）稳定 5.5MB/s。
- 全量 pytest 时 `suite_view_release_20261101` 出现 6 项假败：CPU 满载嵌入（12 块/s）
  挤压该套件的 0.15s/400ms 时序断言；嵌入结束复跑 ALL PASS，与本次改动无关。
